## Project Overview

**Front-end Guidelines** Softonix frontend guidelines repository with architecture best practices example

## Tech Stack

- **Vue 3** with TypeScript, **Vite** for bundling
- **Pinia** for state management
- **Vue Router** for routing
- **Element Plus** for UI components,
- **Tailwind CSS** for styling
- **VueUse** for utilities and composables
- **Axios** for HTTP requests
- **i18n** for translations

## Development Patterns

### Dependency Flow

Strict one-way dependency direction:

```
composable → (store | service)
store → (service | other global stores)
component → (composable | store | service)
```

- **Service**: Pure API/domain logic. NEVER knows about stores, composables
- **Store**: Shared state (Pinia). Can use services and other global/shared stores. NEVER uses project composables
- **Composable**: Business logic orchestrator. Can use stores and services

**Do NOT create stores for single-view state — only for shared state across multiple areas.**

### Where Does a Module Live?

Walk this decision tree for any new store / service / composable / component:

1. **Reusable across multiple modules?**
   - No → keep it view/feature-scoped, co-located inside the owning view/feature.
   - Yes → continue.
2. **Domain-agnostic?** (generic utility, not tied to any business domain)
   - Yes → matching global root folder: `src/store/`, `src/services/`, `src/composables/`, `src/components/`. Examples: `<MoneyInput>`, `useAbortController`, `useFormConfig`.
   - No (tied to a domain) → continue.
3. **How many artifact types does the domain bundle?**
   - One only (e.g. speech recognition = just a service) → matching global root folder (`src/services/general.service.ts`, a lone `src/store/general.store.ts`, etc.).
   - Multiple, **without** its own views (e.g. auth = store + service + types) → `src/features/<domain>/`.
   - Multiple, **including** views (services + components + stores + pages under one domain) → `src/views/<domain>/`.

Rule of thumb: don't wrap a single file in a feature just to give it a folder, and don't scatter a cohesive multi-artifact domain across root folders.

### Views vs Features

| Question                                     | Views (`src/views/`)                          | Features (`src/features/`)                              |
| -------------------------------------------- | --------------------------------------------- | ------------------------------------------------------- |
| Is it tied to a route / URL?                 | Yes — one route tree owns it                  | No — route-agnostic, pluggable anywhere                 |
| Is it used from multiple route trees?        | No — consumed under a single route tree       | Yes — reused across 2+ independent views                |
| Can it have its own service/store?           | Yes — co-located in the view folder           | Yes — co-located in the feature folder                  |
| Does it depend on other features?            | Can orchestrate features                      | NEVER depends on other features                         |
| "It feels like a domain" — where does it go? | Still `views/` if only one route tree uses it | `features/` only if multiple route trees import from it |

### Error Handling

API errors are handled by the **response interceptor** (`src/features/platform/api/interceptors/response.interceptor.ts`) which provides global error handling (e.g., ElNotification, sentry logging, redirects on 401).

### Auto-Imports

The application has configured auto-imports. Check [auto-imports config](./.config/auto-imports/) to see what is available without explicit imports. Everything else requires explicit import.

## General Rules

- Always prefer Vue.js modern API (defineModel instead of props/emits, useTemplateRef for template refs, instead of plain ref, etc)
- All user-facing text must use i18n — `$t('key')` in templates, `t('key')` from `useI18n()` in scripts
- Always use `<Icon name="x" />` for icons (`src/features/platform/icons/assets/`), never inline SVG. If the icon doesn't exist, ask the user to install it. Refer to `src/features/platform/icons/icons.d.ts` -> TIcons autogenerated type to get the list of available icons
- Cross-feature communication via EventEmitter (`src/utils/helpers.ts`) only — never direct imports between features
- Small reusable helper functions go in `src/utils/helpers.ts` (auto-imported as `helpers.xxx`). Check VueUse first before creating a new one
- Data formatting functions (price, phone, date) go in `src/utils/filters.ts` (available as `$filters.xxx` global property in templates scripts)
- Use Tailwind inline classes — no `<style scoped>` blocks
- Check VueUse before creating composables, check Element Plus before creating UI components
- All API types auto-generated in [Schema](./src/features/platform/api/schema.ts) via `openapi-generate` command. Define API types in `.types.d.ts` using schema helpers (`TResponse`, `TRequestBody`) from `src/features/platform/api/dts/schema-helpers.d.ts` — never duplicate API shapes manually
- Use predefined [typography classes](./agent-docs/typography.md) before falling back to raw Tailwind text utilities
- Naming: components are `PascalCase.vue`, TS files are `kebab-case.ts`. Files inside a view or feature are prefixed with the domain name — e.g. `SeniorProfileInfoCard.vue`, `senior-request.service.ts`, `volunteer-request.types.d.ts`
